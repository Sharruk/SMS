SECTION 1: PROJECT OVERVIEW (say this in your interview)
================================================================================

WHAT IS IT?
-----------
A console-based Learning Management System (LMS) built in Java.
It manages students, teachers, and admins of an educational institution
through a role-based login system with full CRUD operations.

All data is stored in plain .txt files using a CSV (comma-separated values)
format — no external library or database needed.

WHAT DOES IT DO?
-----------------
- Three roles: Admin, Teacher, Student — each gets their own menu
- Admin can: add/update/delete/search/sort students, add teachers,
  create courses, assign teachers to courses, enroll students in courses,
  assign grades, create assignments, view system reports
- Teacher can: view their courses, manage grades, create/delete assignments,
  view all students
- Student can: view their enrolled courses, check their grades, see assignments

HOW DOES DATA PERSIST?
------------------------
Each entity has its own plain text file in the data/ folder:
    data/students.txt   — one student per line, CSV format
    data/teachers.txt   — one teacher per line
    data/admins.txt     — admin accounts
    data/courses.txt    — course records
    data/grades.txt     — grade records
    data/assignments.txt — assignment records

When the app starts, each Manager class reads its file into a List in memory.
Every add/update/delete operation writes the entire updated List back to disk.

----------------------------------------------------------------------
1. ENCAPSULATION
----------------------------------------------------------------------
WHERE: Every model class — User, Student, Teacher, Admin, Course, Grade, Assignment

WHAT IT IS:
  All fields are declared PRIVATE. They can only be accessed through
  public getters and setters. This protects the data from direct modification.

EXAMPLE (from User.java):
  private int    id;
  private String name;
  private String email;
  private String password;

  public int    getId()           { return id; }
  public void   setId(int id)     { this.id = id; }
  public String getName()         { return name; }
  public void   setName(String n) { this.name = n; }

WHY IT MATTERS:
  If someone wants to change a student's name, they MUST call setName().
  You cannot write  student.name = "" directly — the compiler blocks it.
  This means you can add validation inside setName() later without breaking
  any code that calls it.

HOW TO EXPLAIN IN 30 SECONDS:
  "I used encapsulation in all my model classes. Every field is private, so
  no outside code can change it directly. Access is always through getters
  and setters. For example, in Student.java, the id field is private and can
  only be read with getId() — nobody can accidentally set it to a negative
  number without us adding a check in setId()."

----------------------------------------------------------------------
2. INHERITANCE
----------------------------------------------------------------------
WHERE: Student, Teacher, Admin all extend User.
       ValidationException, RecordNotFoundException extend AppException.

WHAT IT IS:
  A child class automatically gets all the fields and methods of its
  parent class. The child can also add its own unique fields and methods.

CLASS HIERARCHY:
    User (abstract)
     ├── Student
     ├── Teacher
     └── Admin

  Exception hierarchy:
    AppException
     ├── ValidationException
     └── RecordNotFoundException

EXAMPLE (from Student.java):
  public class Student extends User {
      private String department;  // Student-specific field
      private String batch;       // Student-specific field

      public Student(int id, String name, ...) {
          super(id, name, email, username, password); // calls User constructor
          this.department = department;
          this.batch = batch;
      }
  }

WHAT STUDENT GETS FOR FREE (from User):
  - id, name, email, username, password fields
  - login() method
  - logout() method
  - toString() method
  - All getters and setters

WHY IT MATTERS:
  Without inheritance, you would copy-paste the same id/name/email/login()
  code into Student, Teacher, and Admin — that is a DRY (Don't Repeat
  Yourself) violation. One change in the parent class automatically
  propagates to all three child classes.

HOW TO EXPLAIN IN 30 SECONDS:
  "All three user types — Student, Teacher, Admin — extend an abstract User
  class. The common fields like id, name, email, and common methods like
  login() and logout() are defined once in User. Each subclass only adds
  what's unique to it. For example, Student adds a department and batch,
  while Teacher adds a department. This avoids code duplication."

----------------------------------------------------------------------
3. ABSTRACTION
----------------------------------------------------------------------
WHERE: User.java is an abstract class with two abstract methods.

WHAT IT IS:
  An abstract class defines WHAT methods must exist, but doesn't always
  say HOW they work. You cannot create an object of an abstract class
  directly — you must use a subclass.

EXAMPLE (from User.java):
  public abstract class User {
      // Concrete method — same for everyone
      public void login() {
          System.out.println("Welcome, " + name + "! Logged in as " + getRole() + ".");
      }

      // ABSTRACT methods — must be implemented by every subclass
      public abstract String getRole();
      public abstract void displayMenu();
  }

  This forces every subclass (Student, Teacher, Admin) to provide their
  own implementation of getRole() and displayMenu().

  You cannot write: User user = new User(...)  ← COMPILER ERROR
  You must write:   User user = new Student(...) ← correct

WHY IT MATTERS:
  It's a contract. If someone adds a new role class (e.g., Principal) and
  forgets to write getRole(), the code will not compile. The abstract keyword
  enforces this automatically.

HOW TO EXPLAIN IN 30 SECONDS:
  "I used an abstract class User to define the structure all user roles must
  follow. getRole() and displayMenu() are abstract methods — the compiler
  forces every subclass to implement them. You can't create a User object
  directly; you always create a Student, Teacher, or Admin. This ensures no
  role is ever created without specifying its role name and its menu."

4. POLYMORPHISM
----------------------------------------------------------------------
WHERE: Main.java — the login system and menu routing.

WHAT IT IS:
  A single variable of parent type (User) can refer to objects of different
  child types (Student, Teacher, Admin). When you call a method on it,
  the CORRECT version for the actual object runs — not the parent's version.

EXAMPLE (from Main.java):
  // After login, we have a User reference
  Admin   admin   = adminManager.findByLogin(username, password);
  Teacher teacher = teacherManager.findByLogin(username, password);
  Student student = studentManager.findByLogin(username, password);

  // Calling login() on each — same method name, DIFFERENT behaviour
  admin.login();    // prints "Welcome, System Admin! Logged in as ADMIN."
  teacher.login();  // prints "Welcome, Dr Emma! Logged in as TEACHER."
  student.login();  // prints "Welcome, Alice! Logged in as STUDENT."

  // displayMenu() also uses polymorphism
  admin.displayMenu();    // shows Admin's menu with 6 options
  teacher.displayMenu();  // shows Teacher's menu with 4 options
  student.displayMenu();  // shows Student's menu with 3 options

BEST DEMO — polymorphic array:
  // You can put all three types in one User array
  User[] users = { admin, teacher, student };
  for (User u : users) {
      System.out.println(u.getRole()); // prints ADMIN, TEACHER, STUDENT
      u.login();                       // calls each one's own login()
  }

WHY IT MATTERS:
  The loop code doesn't need to know if it's dealing with an admin,
  teacher, or student. The correct method runs automatically at runtime.
  This is what allows the login system to route users with clean code.

HOW TO EXPLAIN IN 30 SECONDS:
  "Polymorphism is demonstrated in my login system. After finding which
  user logged in, I call login() and displayMenu() through a reference to
  the parent class User. The correct version of the method runs depending
  on the actual object type. If it's a Teacher, Teacher's displayMenu()
  shows 4 options; if it's a Student, Student's 3 options appear. Same
  method call — different behaviour."

5. METHOD OVERRIDING
----------------------------------------------------------------------
WHERE: getRole() and displayMenu() in Student, Teacher, Admin.

WHAT IT IS:
  A subclass provides its own version of a method that is defined in the
  parent class. The @Override annotation is used to tell Java (and the
  developer) that this method is intentionally replacing the parent's version.

EXAMPLE:
  // In User.java:
  public abstract String getRole();  // no implementation — must override

  // In Student.java:
  @Override
  public String getRole() {
      return "STUDENT";  // Student's own version
  }

  // In Teacher.java:
  @Override
  public String getRole() {
      return "TEACHER";  // Teacher's own version
  }

  // In Admin.java:
  @Override
  public String getRole() {
      return "ADMIN";  // Admin's own version
  }

Also — toString() is overridden in every class to give useful output:
  // In User.java:
  public String toString() {
      return "ID: " + id + " | Name: " + name + " | Role: " + getRole();
  }

  // In Student.java:
  @Override
  public String toString() {
      return super.toString() + " | Dept: " + department + " | Batch: " + batch;
  }
  // Output: "ID: 1 | Name: Alice | Role: STUDENT | Dept: CS | Batch: 2022-2026"

WHY IT MATTERS:
  @Override tells the compiler to verify the method actually exists in the
  parent. If you make a typo (getRol() instead of getRole()), the compiler
  will catch it and report an error.

6. METHOD OVERLOADING
----------------------------------------------------------------------
WHERE:
  - Course constructor (2 overloaded versions)
  - The admin can both "enroll student in course" AND "assign course to
    teacher" — conceptually the same action (linking an entity to a course)
    with different parameter types

WHAT IT IS:
  Same method name, different parameter types or count. Java figures out
  which one to call based on what arguments you pass.

EXAMPLE — Constructor Overloading in Course.java:

  // Full constructor (when teacher is known)
  public Course(String courseId, String courseName, int creditHours, String teacherName) {
      this.courseId    = courseId;
      this.courseName  = courseName;
      this.creditHours = creditHours;
      this.teacherName = teacherName;
  }

  // Simplified constructor (teacher not yet assigned)
  public Course(String courseId, String courseName, int creditHours) {
      this(courseId, courseName, creditHours, "Not Assigned"); // calls the first one
  }

  // Usage:
  Course c1 = new Course("CS101", "Java Programming", 3, "Dr Emma");  // 4 args
  Course c2 = new Course("CS202", "Databases", 3);                    // 3 args — overloaded

CONCEPTUAL OVERLOADING — Admin assigning a course:
  // In Main.java, same "assign course" concept works for two different targets:
  courseManager.assignTeacher(courseId, teacher.getName()); // course → teacher
  student.enrollInCourse(courseId);                         // course → student

HOW TO EXPLAIN IN 30 SECONDS:
  "Method overloading is demonstrated in the Course class. It has two
  constructors — one that takes 4 arguments including the teacher name,
  and another that takes 3 arguments and uses 'Not Assigned' as a default.
  Java automatically calls the right constructor based on how many arguments
  you pass. When admin adds a new course, they don't know the teacher yet,
  so the 3-argument version is called."

7. CUSTOM EXCEPTION HANDLING
----------------------------------------------------------------------
WHERE: sms/exceptions/ package (3 classes), used throughout managers and Main.

WHAT IT IS:
  Instead of using Java's generic Exception class, we created our own
  custom exception classes that carry meaningful names and information.

EXCEPTION HIERARCHY:
    java.lang.Exception
     └── AppException          ← our base class
          ├── ValidationException      ← thrown when input is invalid
          └── RecordNotFoundException  ← thrown when a record is missing

EXAMPLE — ValidationException:

  // In InputValidator.java:
  public static void validatePassword(String password) throws ValidationException {
      if (password.length() < 4) {
          throw new ValidationException(
              "Password must be at least 4 characters long", "password"
          );
      }
  }

  // In Main.java — catching it:
  try {
      InputValidator.validatePassword(password);
  } catch (ValidationException e) {
      System.out.println("Validation Error — " + e.getMessage());
      // shows: "Validation Error — Invalid password: Password must be at least 4 characters"
  }

EXAMPLE — RecordNotFoundException:

  // In StudentManager.java:
  public Student findById(int id) throws RecordNotFoundException {
      for (Student s : students) {
          if (s.getId() == id) return s;
      }
      throw new RecordNotFoundException("Student with ID " + id + " not found.");
  }

  // In Main.java:
  try {
      Student s = studentManager.findById(999); // ID doesn't exist
  } catch (RecordNotFoundException e) {
      System.out.println("Error: " + e.getMessage());
      // shows: "Error: Student with ID 999 not found."
  }

WHY CUSTOM EXCEPTIONS?
  Generic Exception only has a message string. Our custom exceptions:
  - Have meaningful class names (you know what went wrong from the name alone)
  - ValidationException stores the fieldName (tells you WHICH field failed)
  - They extend AppException, so you can catch all app errors in one catch block
    if needed:  catch (AppException e) { ... }

TRY-CATCH-FINALLY DEMONSTRATION (in Main.java, every input block):
  try {
      int id = Integer.parseInt(scanner.nextLine());  // may throw NumberFormatException
      Student s = studentManager.findById(id);         // may throw RecordNotFoundException
      // ... do something with s
  } catch (NumberFormatException e) {
      System.out.println("Please enter a valid number.");
  } catch (RecordNotFoundException e) {
      System.out.println("Error: " + e.getMessage());
  }

8. FILE HANDLING
----------------------------------------------------------------------
WHERE: FileHandler.java + every Manager class's loadFromFile/saveToFile

WHAT IT IS:
  Reading data from and writing data to plain .txt files using standard
  Java I/O classes.

CLASSES USED:
  - java.io.BufferedReader  — reads lines efficiently from a file
  - java.io.FileReader      — opens a file for character reading
  - java.io.BufferedWriter  — writes lines efficiently to a file
  - java.io.FileWriter      — opens a file for character writing
  - java.io.File            — represents the file path on disk

READING EXAMPLE (from FileHandler.java):
  public static List<String> readLines(String filePath) {
      List<String> lines = new ArrayList<>();

      try (BufferedReader reader = new BufferedReader(new FileReader(filePath))) {
          String line;
          while ((line = reader.readLine()) != null) {
              if (!line.trim().isEmpty()) {
                  lines.add(line.trim());
              }
          }
      } catch (IOException e) {
          System.err.println("Error reading file: " + e.getMessage());
      }

      return lines;
  }

WRITING EXAMPLE (from FileHandler.java):
  public static void writeLines(String filePath, List<String> lines) {
      try (BufferedWriter writer = new BufferedWriter(new FileWriter(filePath))) {
          for (String line : lines) {
              writer.write(line);
              writer.newLine();
          }
      } catch (IOException e) {
          System.err.println("Error writing file: " + e.getMessage());
      }
  }

NOTE: try-with-resources (the "try (...)" syntax) automatically closes the
BufferedReader/Writer when the block ends — even if an exception occurs.
This prevents file handle leaks.

HOW DATA IS FORMATTED (CSV):
  students.txt format: id,name,email,username,password,department,batch,courseIds
  Example line: 1,Alice Johnson,alice@student.edu,alice,stud123,Computer Science,2022-2026,CS101;CS201

  The 8th field (courseIds) uses semicolons to separate multiple course IDs
  since commas are already used as the column separator.

  Student.toFileString() converts the object to this CSV line.
  Student.fromFileString(line) parses the CSV line back into a Student object.

COMPLETE FLOW:
  1. App starts
  2. StudentManager constructor calls loadFromFile()
  3. loadFromFile() calls FileHandler.readLines("data/students.txt")
  4. FileHandler returns List<String> of raw CSV lines
  5. Each line is passed to Student.fromFileString(line) → Student object
  6. Students are stored in List<Student> in memory
  7. When admin adds a new student → addStudent() is called
  8. New student added to the in-memory List<Student>
  9. saveToFile() is called → iterates list, calls toFileString() on each
  10. FileHandler.writeLines() overwrites students.txt with the updated list
  11. Next time the app starts, the new student is loaded automatically

9. COLLECTIONS FRAMEWORK
----------------------------------------------------------------------
WHERE: Every Manager class

WHAT IS USED:
  - ArrayList<T>    — stores lists of students, teachers, courses, etc.
  - Stream API      — for searching and filtering (search by name)
  - Comparator      — for sorting with lambda expressions

ARRAYLIST EXAMPLE (StudentManager.java):
  private List<Student> students = new ArrayList<>();

STREAM SEARCH EXAMPLE (StudentManager.java):
  public List<Student> searchByName(String keyword) {
      return students.stream()
          .filter(s -> s.getName().toLowerCase().contains(keyword.toLowerCase()))
          .collect(Collectors.toList());
  }
  // .stream()           : converts list to a stream of elements
  // .filter(predicate)  : keeps only students whose name matches
  // .collect(...)       : converts stream back to a List

LAMBDA SORT EXAMPLE (StudentManager.java):
  public List<Student> sortByName() {
      List<Student> sorted = new ArrayList<>(students);
      sorted.sort((a, b) -> a.getName().compareToIgnoreCase(b.getName()));
      return sorted;
  }
  // (a, b) -> ...  is a lambda expression (anonymous function)
  // It defines HOW to compare two Student objects

  public List<Student> sortById() {
      List<Student> sorted = new ArrayList<>(students);
      sorted.sort((a, b) -> Integer.compare(a.getId(), b.getId()));
      return sorted;
  }

SECTION 5: INTERVIEW QUESTIONS AND STRONG ANSWERS
================================================================================

——— BASIC QUESTIONS ———

Q: Explain your project in 60 seconds.
A: "I built a console-based Learning Management System in Java. It has three
   roles — Admin, Teacher, and Student — with a role-based login system where
   each role sees its own menu. The Admin can register students and teachers,
   create courses, assign teachers to courses, enroll students, manage grades,
   create assignments, and view reports. Teachers can manage grades and
   assignments for their courses. Students can check their courses, grades,
   and assignments.

   Data is stored in plain .txt files in CSV format, using BufferedReader and
   BufferedWriter for file I/O. The project demonstrates all major OOP
   concepts: encapsulation in the model classes, inheritance through a User
   hierarchy, abstraction via an abstract User class, polymorphism in the login
   and menu system, method overriding in getRole() and displayMenu(), method
   overloading in the Course constructors, custom exceptions, and file
   handling."

Q: What is the purpose of the User class?
A: "User is an abstract base class that all three role classes extend — Student,
   Teacher, and Admin. It holds the common data that every user has: id, name,
   email, username, and password — all private with getters and setters for
   encapsulation. It also provides the shared login() and logout() methods that
   are inherited by all three roles.

   It declares getRole() and displayMenu() as abstract methods, which forces
   every subclass to implement them. You cannot create a User object directly —
   the compiler won't allow it. You always create a specific role like Student
   or Teacher."

Q: Why did you use .txt files instead of a database?
A: "For a student-level project, a plain text file with CSV format achieves the
   same goal — persisting data between sessions — with much less complexity.
   It needs zero external setup, zero dependencies, and the file is human-
   readable: you can open students.txt in any text editor and see the data.

   The architecture is designed so switching to a database later would be
   easy: the Manager classes handle all I/O. You would just replace the
   loadFromFile() and saveToFile() methods with SQL queries. The rest of
   the application would not change."

Q: How does the login system work?
A: "The login loop in Main.java asks for a username and password, then checks
   all three data sources in order. First it tries AdminManager.findByLogin(),
   then TeacherManager.findByLogin(), then StudentManager.findByLogin(). Each
   of these iterates its in-memory list comparing username and password strings.

   If a match is found, the login() method is called on that object — which
   is a polymorphic call, because login() is defined in User but the actual
   object is an Admin, Teacher, or Student. Then the corresponding menu handler
   method is called. If no manager finds a match, 'Invalid credentials' is shown
   and the loop repeats."

——— INTERMEDIATE QUESTIONS ———

Q: Explain polymorphism with a specific example from your code.
A: "The clearest example is in the login system in Main.java. After identifying
   which user logged in, I call login() and displayMenu() on each user object.

   For example:
     admin.login()    prints 'Welcome, System Admin! Logged in as ADMIN.'
     teacher.login()  prints 'Welcome, Dr Emma! Logged in as TEACHER.'
     student.login()  prints 'Welcome, Alice! Logged in as STUDENT.'

   All three call the same login() method defined in User, but they each also
   call getRole() inside it — and getRole() is overridden in every subclass to
   return a different string. So the same method call produces different output
   depending on the actual object type.

   The best demo is a User array:
     User[] users = { admin, teacher, student };
     for (User u : users) {
         u.displayMenu();  // calls Admin's menu, then Teacher's, then Student's
     }
   The loop doesn't need an if-else chain or type checking. Polymorphism
   handles it automatically."

Q: What is the difference between an abstract class and an interface?
   Which did you use and why?
A: "An abstract class can have both implemented (concrete) methods AND abstract
   methods. It can also have fields (instance variables). An interface (before
   Java 8) can only have abstract methods — no implementation, no fields.

   I used an abstract class for User because all three role classes genuinely
   share working code: the login() method, the logout() method, and all the
   getters and setters are implemented in User and inherited by the subclasses.
   If I used an interface, I couldn't put that shared code there — each subclass
   would have to copy it.

   I chose abstract class when there is real shared behaviour.
   I would use an interface when I just need a contract — when I want to
   guarantee a class has certain methods but there's no shared implementation."

Q: How does your file persistence work in detail?
A: "Every Manager class follows the same pattern — StudentManager is a good
   example.

   When the constructor runs at startup, it calls loadFromFile(). This calls
   FileHandler.readLines('data/students.txt'), which opens the file with a
   BufferedReader wrapping a FileReader, reads every non-empty line, and
   returns a List<String>.

   Each line looks like: 1,Alice Johnson,alice@student.edu,alice,stud123,CS,2022-2026,CS101;CS201

   loadFromFile() passes each line to Student.fromFileString(line), which
   splits on commas, creates a new Student object, and also parses the 8th
   field (semicolon-separated course IDs) to populate the enrolled courses list.

   Whenever a student is added, updated, or deleted, saveToFile() runs.
   It iterates the in-memory List<Student>, calls toFileString() on each student
   to convert it back to CSV format, and passes the resulting List<String> to
   FileHandler.writeLines(), which uses a BufferedWriter wrapping a FileWriter
   to overwrite the file.

   BufferedReader and BufferedWriter are more efficient than plain FileReader
   and FileWriter because they use an internal buffer — they don't access the
   disk for every single character."

Q: What is method overloading? Where is it in your project?
A: "Method overloading means having two or more methods with the same name but
   different parameter lists. Java uses the number or types of arguments at the
   call site to decide which version to execute — this is resolved at compile
   time.

   In my project, the Course class has two constructors with the same name
   (Course) but different numbers of parameters:

   Course(String courseId, String courseName, int creditHours, String teacherName)
   Course(String courseId, String courseName, int creditHours)

   The 3-argument version calls the 4-argument version using 'Not Assigned' as
   the default teacher name. When admin creates a new course from the menu,
   they don't know the teacher yet, so the 3-argument version is called:
     new Course(courseId, courseName, credits)

   When loading a course from the file (where all 4 fields are stored), the
   4-argument version is used:
     Course.fromFileString(line) → new Course(id, name, credits, teacherName)"

Q: What is the difference between method overriding and overloading?
A: "Overriding is a runtime concept. A subclass provides its own version of a
   method that exists in the parent class. The method signature is IDENTICAL
   in the parent and child — same name, same parameter types, same return type.
   When called at runtime, the subclass version runs. Example: getRole() is
   declared in User, overridden in Student, Teacher, Admin. Which version runs
   depends on the actual object type.

   Overloading is a compile-time concept. The same class (or related classes)
   has multiple methods with the same name but DIFFERENT parameter lists. Java
   picks the right one at compile time based on the arguments. Example: Course
   has two constructors with 3 and 4 parameters.

   Simple way to remember:
   Overriding = same signature, different class (parent vs child), runtime decision.
   Overloading = same name, different parameters, same class, compile-time decision."

Q: What are custom exceptions and why did you use them?
A: "Java's built-in Exception class only carries a message string. My custom
   exceptions carry more specific information and have meaningful names.

   I have AppException as the base, and two subclasses:
   - ValidationException: thrown by InputValidator when input fails a rule.
     It stores fieldName so you know WHICH field was invalid.
   - RecordNotFoundException: thrown by Manager classes when findById() gets
     an ID that doesn't exist.

   Using custom exceptions makes error messages clearer. When a student ID
   doesn't exist, the error says 'Student with ID 999 not found' instead of
   a generic message. It also makes catch blocks cleaner — I can catch
   ValidationException and RecordNotFoundException separately and respond
   differently to each one. If I catch both as AppException, I handle all
   app-specific errors in one place."

——— DEEP TECHNICAL QUESTIONS ———

Q: Why do Student, Teacher, Admin each have toFileString() and fromFileString()?
   Isn't that bad OOP?
A: "It's a valid question. In a more advanced design, you could have a Serializable
   interface or a separate converter class. But for a 5th semester project, having
   toFileString() and fromFileString() directly on the model class is actually
   clean and simple. The model knows its own structure best — it knows which fields
   exist and in what order. Putting that logic there avoids creating a separate
   adapter layer just for CSV conversion.

   The alternative would be a FileConverter class for each model, which adds
   more files and complexity without much benefit at this scale. The goal was
   to keep the code readable and easy to explain, and this achieves that."

Q: Why is the enrolled course list stored as semicolons in the student's file line
   instead of a separate enrollment file?
A: "Simplicity. The alternative would be a student_courses.txt file with lines
   like studentId,courseId — that's a many-to-many relationship table, which
   is how a real database would handle it.

   For this project, storing course IDs as a semicolon-separated 8th field keeps
   everything about a student in one line. It's simple to read and write. The
   only rule I had to enforce is that course IDs themselves don't contain semicolons
   or commas, which is naturally satisfied by IDs like CS101, IT201, etc.

   If I needed to add more complex relationships, a separate file would be the
   right approach."

Q: What happens if you run the app and data/students.txt doesn't exist?
A: "FileHandler.readLines() checks if the file exists before opening it:
     File file = new File(filePath);
     if (!file.exists()) return new ArrayList<>();

   So if the file doesn't exist, loadFromFile() gets an empty list and
   StudentManager starts with zero students in memory. When the first student
   is added, saveToFile() is called, and FileHandler.writeLines() creates the
   file automatically using:
     file.getParentFile().mkdirs();
   This creates the data/ directory if it doesn't exist, and then creates
   students.txt. The app handles a missing file gracefully without crashing."

Q: Your search is case-insensitive partial match. What if you searched for a
   student by ID instead of name?
A: "Currently searchByName() only searches by name. To search by ID, you would
   call findById(int id) which looks for an exact match. For a combined search
   that accepts either name or ID, I could add a general search method:

   public List<Student> search(String keyword) {
       return students.stream()
           .filter(s -> s.getName().toLowerCase().contains(keyword.toLowerCase())
                     || String.valueOf(s.getId()).equals(keyword))
           .collect(Collectors.toList());
   }

   I kept it separate (searchByName and findById) because in the UI, the admin
   knows whether they're searching by name or looking up a specific ID — they
   serve different purposes."

——— "CHALLENGES" QUESTIONS ———

Q: What was the hardest part of building this project?
A: "The file persistence was the trickiest part, specifically handling the
   student's enrolled course list inside a CSV format. A CSV line uses commas
   as separators, but a student can be enrolled in multiple courses — so I
   needed a second separator level. I used semicolons for the course IDs (the
   8th field): CS101;CS201;IT101.

   The toFileString() method joins the course IDs with ';' and fromFileString()
   splits the 8th field on ';' to reconstruct the list. I also had to use
   split(',', -1) with the limit parameter to handle trailing empty fields
   (like when a student has no courses yet — the 8th field is empty).

   The -1 in split(',', -1) means 'don't discard trailing empty strings,'
   which avoids an ArrayIndexOutOfBoundsException when accessing parts[7] for
   a student with no enrolled courses."

Q: What would you improve if you had more time?
A: "Three things:
   1. Password hashing — currently passwords are stored in plain text in the
      .txt files. I would use a hash function so that even if someone opens
      the file, they can't see the real passwords.
   2. A proper many-to-many enrollment file — instead of storing course IDs
      inside the student's line, I'd create a student_courses.txt with
      studentId,courseId lines, which scales better.
   3. A simple GUI — a Swing or JavaFX interface would make the project
      look more impressive in a demo, even though the console version is
      fully functional."

SECTION 9: DEFENDING WEAKNESSES HONESTLY
================================================================================

Q: Why aren't passwords hashed?
A: "You're right — storing plain text passwords is a security weakness. In a
   production system, I would use BCrypt hashing. For this academic project,
   the focus was demonstrating OOP concepts and file I/O. Adding BCrypt would
   require an external library and shift focus away from the core OOP learning
   goals. I am aware of this limitation and would fix it for any real deployment."

Q: What if two users run the app at the same time?
A: "This application is single-user, console-based — it's not designed for
   concurrent access. If two instances ran simultaneously, they could overwrite
   each other's file writes. A real multi-user system would use a database with
   transaction support, or at minimum a file lock mechanism. This is a known
   limitation of simple file-based persistence."

Q: Doesn't saving the entire list to the file every time a record is changed
   waste performance?
A: "For the scale of this project — dozens to hundreds of records — the overhead
   is negligible. The files are small and rewriting them is nearly instant.
   In a production system with thousands of records, you'd use a database or an
   append-only log. The approach here prioritises simplicity and correctness over
   performance optimisation, which is appropriate for a learning project."

Q: Your Admin class has no extra fields. Isn't that pointless to have a
   separate class?
A: "Even without extra fields, Admin is a separate class for a good reason.
   It overrides getRole() to return 'ADMIN' and provides a completely different
   displayMenu(). Without a separate class, you'd have to store the role as a
   String field in User and add if-else chains everywhere to check what role
   a user is — which violates the Open/Closed principle. A separate class also
   makes it easy to add admin-specific fields or methods in the future without
   touching any other class."
